## 第0部 これは何か

### 一言で

**議論の中身は日本語のまま置いておき、その「あいだの関係」だけを機械が読める形にする。**

### 何ができるようになるか

| できること | 例 |
|---|---|
| いま何が確定していないか、それが何を止めているかが分かる | 「精肉店にまだ電話していない。その1本で3つの決定が止まっている」 |
| 前提が変わったとき、見直すべき範囲が自動で出る | 「アンケートの人数が半分だった → この4件を見直せ」 |
| 誰も突き合わせていない事実が見つかる | 「火気は指定区画のみ、という規約が、どの判断にもつながっていない」 |
| 半年後に、なぜそう決めたのかを再構成できる | 「この案を選んだのは、当時まだ抽選前だったから」 |

### 成立させるための唯一の条件

**「支え」の欄にはIDしか書かない。** 自然言語を1文字でも混ぜた瞬間、上のすべてが動かなくなる。

このマニュアルの規則の大半は、この一点を守りやすくするためにある。

### 向いている場面 / 向いていない場面

| 向いている | 向いていない |
|---|---|
| 期間が長い（週〜年） | その場で終わる |
| 参加者が多い、途中で入れ替わる | 全員が最後まで同席する |
| 前提が途中で覆る | 前提が動かない |
| 間違いのコストが高い | やり直しがきく |
| あとで「なぜそう決めたか」を問われる | 問われない |

短時間の打ち合わせなら、ホワイトボードのほうが速い。

## 第1部 5分でわかる全体像

### 部品は2つだけ

**ノード**（言っていること）と、**エッジ**（関係）。

```
node : 何を主張しているか、という文が1つ
edge : どのノードがどのノードを「支える」か「もう成り立たなくする」か
```

エッジの種類は2つしかない。

- `support` ── 支える
- `rebut` ── もう成り立たなくする

### いちばん小さい例

会話：

> 「雨が降ると気温が下がるからドリンクは売れないよ」
> 「いや、去年の売上一覧を見ると、雨でも変わってないよ」

これをそのまま書くと、こうなる。

```
《経験則》 ──→ [n1] 雨が降ると気温が下がる
《経験則》 ──→ [n2] 気温が下がるとドリンクは売れない
[n1][n2] ──→ [n3] 雨が降るとドリンクは売れない

《記録》  ──→ [n4] 去年の売上一覧では、雨の日もドリンクの売上は落ちていない
[n4]     ⊣    [n2]        ← rebut
```

ポイントが3つある。

1. **「〜から」で1文になっていたものを、n1 と n2 に割った。** 割らないと、反論がどこに刺さるのか書けない。
2. **反論は n3 ではなく n2 に刺さっている。** 「雨でも売れる」と言いたいのではなく、「気温が下がると売れない」という橋を崩している。
3. **`経験則` と `記録` もノードである。** 出所を別フィールドにせず、ノードにして支えさせる。

n2 が倒れると、n1・n2 が揃って支えていた n3 も倒れる。これが自動で出る。

## 第2部 データ定義

### 2.1 ノード

```json
{ "id": "n3", "text": "雨が降るとドリンクは売れない", "at": "2026-09-05", "say": "12" }
```

| フィールド | 必須 | 内容 |
|---|---|---|
| `id` | ○ | 一意の識別子。`n3` `b16` など。接頭辞は人間が読みやすくするためだけのもの |
| `text` | ○ | 主張の全文。**1文・1結論・主語つき** |
| `at` | ○ | いつから有効か。`YYYY-MM-DD` |
| `say` | | 出所の位置。発言番号、ページ番号、ファイル名など |

### 2.2 エッジ

```json
{ "id": "e7", "kind": "support", "from": ["n1","n2"], "to": "n3", "at": "2026-09-05" }
{ "id": "e8", "kind": "rebut", "from": ["n4"], "to": "n2", "at": "2026-09-05",
  "note": "去年の実測と食い違う" }
```

| フィールド | 必須 | 内容 |
|---|---|---|
| `id` | ○ | 一意。**エッジを後から参照するために必要**（省略しないこと） |
| `kind` | ○ | `support` または `rebut` |
| `from` | ○ | ノードIDの**配列**。配列内は連言（後述） |
| `to` | ○ | ノードID |
| `at` | ○ | いつ張られたか |
| `note` | | rebut のとき、何を否定するのか |

### 2.3 ノードとエッジは必ず別配列で持つ

```js
const N = [ {id, text, at}, ... ];     // 関係の情報を一切持たない
const E = [ {id, kind, from, to, at}, ... ];
```

ノードの中に `支え: [...]` を書いてはならない。理由は2つ。

- あとから1本つなぎたくなったとき、ノードの定義を書き換えることになる
- 同じ関係が2箇所に書かれて、不整合が起きる

### 2.4 連言と独立

`from` が配列なのは、**「全部揃って初めて支える」を表すため**。

```
{from:["a","b","c"], to:"x"}            → a・b・c が揃って x を支える（連言）
{from:["a"], to:"x"}
{from:["b"], to:"x"}                    → a と b がそれぞれ独立に x を支える
```

| | 1本崩れたとき |
|---|---|
| 連言 | x も倒れる |
| 独立 | x は残る（支えが減るだけ） |

**これは見た目の問題ではなく、波及計算そのものを変える。**

### 2.5 出所ノード（固定語彙・6語）

議論の外から持ち込んだものは、必ずこの6つのいずれかで支える。**語彙は増やさない。**

| 出所 | 意味 | 例 |
|---|---|---|
| `記録` | 一次資料、規約、その場で確認した事実 | 売上集計、実施要項、アンケート結果 |
| `伝聞` | 人づてに聞いた話。一次資料ではない | 「先輩が1,200食売れたと言っていた」 |
| `経験則` | 一般化されているが、この場では検証されていない | 「飲食は9割立地」 |
| `直感` | 根拠が提示されていない | 「絶対人集まりますって」 |
| `方針` | この場の価値判断。事実ではない | 「売り切れは赤字よりマシ」 |
| `情報不足` | まだ分かっていない | 「区画が良いか悪いか分からない」 |

出所ノードには `at` を持たせない。常に存在する。また、出所ノードが `to` に現れてはならない（出所は支えられない）。

## 第3部 構築フロー

ここが本体。人間でもAIでも、この順に処理する。

### 全体の流れ

```
 ┌─────────────────────────────────────────┐
 │ Step 0  素材を並べる                     │
 │         発言・資料に通し番号をふる        │
 └───────────────┬─────────────────────────┘
                 ▼
 ┌─────────────────────────────────────────┐
 │ Step 1  言い切りに割る          ★最重要  │
 │         接続詞・複数結論を分解する        │
 └───────────────┬─────────────────────────┘
                 ▼
 ┌─────────────────────────────────────────┐
 │ Step 2  ノードにする                     │
 │         主語述語を補い、IDと at をふる    │
 └───────────────┬─────────────────────────┘
                 ▼
 ┌─────────────────────────────────────────┐
 │ Step 3  出所をつなぐ                     │
 │         6語のどれかから support を張る    │
 └───────────────┬─────────────────────────┘
                 ▼
 ┌─────────────────────────────────────────┐
 │ Step 4  ノード間の支えをつなぐ           │
 │         連言か独立かを決める              │
 └───────────────┬─────────────────────────┘
                 ▼
 ┌─────────────────────────────────────────┐
 │ Step 5  反論をつなぐ                     │
 │         刺す先が結論か橋かを見極める      │
 └───────────────┬─────────────────────────┘
                 ▼
 ┌─────────────────────────────────────────┐
 │ Step 6  疑問を処理する                   │
 │         条件形か「分からない」形か        │
 └───────────────┬─────────────────────────┘
                 ▼
 ┌─────────────────────────────────────────┐
 │ Step 7  検算する                         │
 │         参照・循環・浮きノードを確認      │
 └─────────────────────────────────────────┘
```

---

### Step 0 ── 素材を並べる

書き起こし、議事録、メモ、資料に**通し番号**をふる。これが `say` になる。

あとで「この主張はどこから来たのか」を確認できるようにするため。番号がないと、記録者が補完したのか、本当に言われたのかが区別できなくなる。

---

### Step 1 ── 言い切りに割る ★最重要

**1つの発言を、1つずつ独立に真偽を問える文に分解する。**

このステップの品質が、全体の品質をそのまま決める。

#### 判定：割るか、割らないか

次のどれかに当てはまったら **割る**。

| 合図 | 例 |
|---|---|
| 「〜のため」「〜だから」「〜なので」「〜ゆえに」 | 雨が降ると気温が下がる**ため**ドリンクは売れない |
| 「〜だし、〜だから」（理由が2つ以上） | 人員が足りない**し**、競合にも勝てない**から**やめよう |
| 結論が2つ以上ある | 仕込みはできる。**しかし**模倣はやめたほうがいい |
| 事実と評価が混ざっている | 原価率20%で、**これは非常に優秀な数字だ** |

#### なぜ割るのか

**議論で最も攻撃されるのは、事実でも結論でもなく、そのあいだの橋である。**

橋が文の中に埋まっていると、誰もそこを攻撃できない。

```
✗ 割っていない
  [n3] 雨が降ると気温が下がるためドリンクは売れない
        ↑ 「気温が下がるとドリンクが売れない」を否定したくても、刺す先がない

○ 割った
  [n1] 雨が降ると気温が下がる
  [n2] 気温が下がるとドリンクは売れない       ← ここを攻撃できる
  [n3] 雨が降るとドリンクは売れない  ← {n1, n2}
```

#### 分解の手順

1. 発言から**結論**を抜き出す（「だから何が言いたいのか」）
2. その結論を支える**理由**を抜き出す
3. 理由と結論のあいだにある**橋**（言われていないが必要な一般則）を探す
4. 橋が明示されていたら、それもノードにする
5. **橋が明示されていなければ、書かない**（→ D1 参照）

#### 例：実際の発言を割る

> **若林**：肉の原価が高すぎるんですよ。丼で満足させようと思ったら150gは要るじゃないですか。安い部位でもグラム150円として、肉だけで225円。米とタレと容器で50円。原価300円弱。

| ID | text |
|---|---|
| s2 | ステーキ丼で客を満足させるには肉が1食150g必要で、安い部位でもグラム150円として肉だけで原価225円になる |
| s3 | ステーキ丼の原価は、米・タレ・容器の50円を含めて1食300円弱になる |

s3 は s2 に支えられる。「原価が高すぎる」という評価そのものは、この時点では別ノードにしない（数字の提示で終わっているため）。

---

### Step 2 ── ノードにする

割った文を、**単体で読んで意味が通る形**に書き直す。

#### 規則：主語・述語・目的語を書く

```
✗  残りは全部廃棄した
○  ラグビー部は、去年売れ残った約680食分の食材をすべて廃棄した

✗  それ、収益的にはどうするんですか
○  （疑問文は Step 6 で処理する。ここでは飛ばす）

✗  原価率50%
○  ステーキ丼を600円で売ると原価率50%、1食あたりの利益は300円になる
```

半年後に初めて読む人が、そのノードだけを見て意味を取れるか。それが基準。

#### 規則：条件とスコープは文中に埋める

```
✗  飲料は売れない
○  気温が低い日は、屋外で販売される冷たい飲料の需要が落ちる
```

「屋外」「冷たい」を落とすと、温かい飲み物についての主張と誤って衝突判定される。

#### IDと日付をふる

- `id` ── 話題ごとに接頭辞を分けると読みやすい（`y1` 去年の失敗、`b3` 豚バラ串、など）。機械は見ないので自由
- `at` ── その発言があった日付
- `say` ── 通し番号

---

### Step 3 ── 出所をつなぐ

各ノードについて、**議論の外から持ち込まれたものかどうか**を判定する。

外から来たものなら、6語のいずれかから `support` を張る。

#### 判定フロー

```
その内容は、この議論の中で他の主張から導かれたか？
│
├─ YES → 出所は不要。Step 4 でノード同士をつなぐ
│
└─ NO  → 外から持ち込まれたもの。以下で出所を選ぶ
         │
         ├─ まだ分かっていない？ ───────────→《情報不足》
         │
         ├─ 「〜すべき」「〜のほうが大事」など
         │   価値判断か？ ────────────────→《方針》
         │
         ├─ 根拠がまったく示されていない？ ──→《直感》
         │   （「絶対〜ですって」「〜な気がする」）
         │
         ├─ 資料・規約・その場で確認した事実？→《記録》
         │
         ├─ 人づてに聞いた話？ ─────────────→《伝聞》
         │
         └─ 一般論として述べられたが、
             この場では検証されていない？ ───→《経験則》
```

#### 判定の勘所

| 迷いやすい | どちらか | 理由 |
|---|---|---|
| 「PS5は7,000〜8,000万台売れているはず」 | `記録`ではなく**要注意** | 「はず」は記憶。厳密には `伝聞` に近いが、公表数値を指しているなら `記録` とし、`text` に「〜と記憶している」を残す |
| 「先輩が1,200食売れたと言っていた」 | `伝聞` | 一次資料ではない。**ここを `記録` にすると最大の失敗要因が見えなくなる** |
| 「飲食は9割立地」 | `経験則` | 一般化されているが検証されていない |
| 「売り切れは赤字よりマシ」 | `方針` | 事実ではなく、何を重視するかの選択 |
| 「絶対人集まりますって」 | `直感` | 理由が示されていない。**無理に理由を探して書かない** |

---

### Step 4 ── ノード間の支えをつなぐ

導かれた主張について、**何がそれを支えているか**をエッジで書く。

#### 判定：連言か独立か

支えが2つ以上あるとき、次を問う。

> **その1つが崩れたら、この結論も崩れるか？**

| 答え | 書き方 |
|---|---|
| はい（全部必要） | `{from:["a","b","c"], to:"x"}` ── 1本のエッジにまとめる |
| いいえ（それぞれ単独でも支持） | `{from:["a"], to:"x"}` `{from:["b"], to:"x"}` ── 別々のエッジ |

#### 例

```
[b16] ラグビー部は、豚バラ串を1本250円で主力商品として販売する
      ← {b4 条件を満たす, b8 原価率が優秀, b11 作業時間が解決, b14 発注できる}
```

これは**連言**。b14（精肉店に発注できる）が崩れたら、この決定は成り立たない。だから1本のエッジにまとめる。

```
[c8] A案を採用すべきである
      ← {G2 写真映えする}
      ← {V2 話題性を優先する}
```

これは**独立**。片方が崩れても、もう片方の理由は残る。だからエッジを2本に分ける。

#### よくある誤り

迷ったら**連言にする**のが安全、と考えがちだが逆。連言にすると波及範囲が広く出るので、**関係ない見直しが大量に発生する**。実際にそれで誤検出が起きた事例がある。

「本当に全部必要か」を1つずつ問うこと。

---

### Step 5 ── 反論をつなぐ

#### 判定：反論かどうか

「でも」「ただ」「いや」で始まっていても、反論とは限らない。次を問う。

> **その発言は、先の主張を成り立たなくするか？ それとも、認めたうえで何かを足しているか？**

| 発言 | 判定 |
|---|---|
| 「ハードの利益率が足を引っ張ってる。ただ、インストールベース自体が資産だとは思う」 | **反論ではない**。前の主張を認めたうえで別の観点を足している |
| 「n人いれば仕込みはできる」（前の「人員が足りない」に対して） | **反論**。前の主張が成り立たなくなる |
| 「ただ、怖がられないようにしてくださいね」 | **反論ではない**。条件を足している。新しいノードの支えにする |

反論でないなら、エッジを張らない。**「でも」を全部 rebut にすると、グラフが対立だらけになって使えなくなる。**

#### 判定：どこに刺すか

反論だと分かったら、次を問う。

> **相手の結論そのものを否定しているのか、それとも「事実は認めるが、そこからその結論は出ない」と言っているのか。**

| 言っていること | 刺す先 |
|---|---|
| 結論そのものが違う | 結論のノード |
| 事実は認めるが、そこからその結論は出ない | **その橋のノード**（Step 1 で割ったもの） |

後者を書けるかどうかが、Step 1 で正しく割れたかの答え合わせになる。**刺す先の橋が存在しなければ、割り足りていない。**

```
「方向性は同意なんですが、IPを当てること自体はギャンブルですよね」
  → 結論（IP多面展開をすべき）は否定していない
  → 「IPを押さえれば継続収益になる」という橋を崩している
  → 橋のノードに刺す
```

#### note を必ず書く

`note` に「何を否定しているのか」を1文で書く。あとで読んだとき、これがないと何が起きたのか分からなくなる。

---

### Step 6 ── 疑問を処理する

疑問文はそのままではノードにできない。**2種類のどちらかに変換する。**

#### 判定フロー

```
その疑問に答えが出たとき、いま出ている判断はどうなるか？
│
├─ 「はい」なら判断が成り立ち、「いいえ」なら倒れる
│      → 【条件形】として書く
│        text : 「〜できる」「〜である」（肯定の平叙文）
│        支え :《情報不足》
│
└─ 「はい」でも「いいえ」でも、その判断の理由が消える
       → 【分からない形】として書く
         text : 「〜か、まだ分からない」
         支え :《情報不足》
```

#### 見分けの一問

> **答えがどちらに転んでも、その判断の理由が消えるか？**

消えるなら【分からない形】。

#### 例：条件形

> 「高橋さんの実家の精肉店に頼めるかな」

B案の実行は「頼める」ことを**必要としている**。頼めなければ倒れる。だから条件形。

```
[b14] ラグビー部は、OB会経由で高橋さんの実家の精肉店に串打ち済みの豚バラ串を発注できる
      ←《情報不足》
```

#### 例：分からない形

> 「今年の場所ってもう決まってるのか」

「立地に依存しない案を選ぶべき」という判断が要るのは、**決まっていないから**である。

| 抽選の結果 | 判断はどうなるか |
|---|---|
| 良い区画だった | 立地を活かす案のほうが強い。この判断は不要 |
| 悪い区画だった | 悪条件に特化すべき。この判断は不要 |

どちらでも不要になる。だから【分からない形】。

```
[x2] ラグビー部の今年の出店区画が良い場所か悪い場所か、まだ分からない
      ←《情報不足》
[x3] ラグビー部は、どの区画に当たっても成立する出店案を選ぶべきである
      ← {x1 立地で売上がほぼ決まる, x2, x_方針}
```

#### やってはいけない

【分からない形】を条件形に押し込むと、**読めない文になる。**

```
✗ [l3] ラグビー部は、今年の抽選で人通りの多い区画を引き当てる  ←《情報不足》
  [l5] ラグビー部は、どの区画に当たっても成立する案を選ぶべきである ← {l3, ...}

  → 「良い区画に当たるから、区画に依存しない案を選ぶべき」と読める。逆である。
```

#### 「なぜ分からないのか」が判明したら

語彙を増やさず、ノードを1つ足して支えさせる。

```
[x2]  区画が良い場所か悪い場所か、まだ分からない       ←《情報不足》
[x2a] 抽選は来週なので、現時点では誰にも分からない     ←《記録》  → x2 を支える
```

`x2a` があるものは待つしかない。ないものは調べれば済むかもしれない。

**記録の時点でこれを判定させてはならない。** 会話から分からないことのほうが多い。分かったときだけ書く。

---

### Step 7 ── 検算する

機械的に確認できることが5つある。

| 確認項目 | 内容 |
|---|---|
| 参照整合 | `from` / `to` が実在するIDを指しているか |
| 循環 | 閉路がないか（あれば Step 1 の割り方を疑う） |
| 出所の位置 | 出所ノードが `to` に現れていないか |
| 語彙 | 出所が6語のいずれかか |
| 浮きノード | 出力エッジがゼロのノードを一覧する |

**浮きノードの一覧は必ず目視する。** 2種類が混ざっている。

- **結論** ── これで正しい（最終決定は誰も使わない）
- **使われていない資料** ── 見落としの可能性がある

区別は「支えが出所だけか」で機械的にできる。出所だけに支えられて出力ゼロなら、使われていない資料。

> 実例：出店会議で「大学は火気使用を指定区画のみに限る」という規約が浮いていた。豚バラ串は焼き台を使うのに、この制約と一度もつながっていなかった。しかも「どの区画でも成立する案を選ぶ」という前提と衝突する可能性がある。会議中は誰も気づいていない。

## 第4部 判定表

迷ったときに引く早見表。

### 4.1 割るか

| 合図 | 判定 |
|---|---|
| 「〜のため」「〜だから」「〜なので」 | 割る |
| 理由が2つ以上 | 割る |
| 結論が2つ以上 | 割る |
| 事実＋評価 | 割る |
| 数字の列挙だけ | 割らなくてよい（1ノードにまとめる） |

### 4.2 出所はどれか

| 発言の特徴 | 出所 |
|---|---|
| 資料名・規約・アンケート結果が挙がっている | `記録` |
| 「〜って言ってた」「〜らしい」 | `伝聞` |
| 「〜って言われるくらいで」「一般に〜」 | `経験則` |
| 「絶対〜」「〜な気がする」「なんとなく」 | `直感` |
| 「〜すべき」「〜のほうが大事」「〜を優先したい」 | `方針` |
| 「〜かな」「〜どうなんだろう」「未定」 | `情報不足` |

### 4.3 support か rebut か

| 発言の中身 | 判定 |
|---|---|
| 前の主張が成り立たなくなる | `rebut` |
| 前の主張を認めたうえで観点を足す | エッジを張らない。新ノードにする |
| 前の主張に条件を付ける | エッジを張らない。両方を支えとする新ノードを作る |
| 前の主張を言い換えただけ | ノードを作らない（既存を使う） |

### 4.4 連言か独立か

| 問い | 判定 |
|---|---|
| その1つが崩れたら結論も崩れるか → はい | 連言（1本のエッジ） |
| その1つが崩れても結論は残るか → はい | 独立（別々のエッジ） |
| 分からない | **独立にしておく**（連言にすると波及が過大に出る） |

### 4.5 疑問の書き方

| 問い | 判定 |
|---|---|
| 「はい」なら判断が立ち、「いいえ」なら倒れるか | 条件形 |
| どちらでも判断の理由が消えるか | 分からない形 |

## 第5部 更新のしかた

### 5.1 唯一の運用規則：追記のみ

**既存のノードとエッジを書き換えない。削除しない。**

訂正したいときは `rebut` を張る。これを守ることが、時点復元が成立する唯一の条件。

### 5.2 新しい情報が来たとき

抽選の結果が出た、という場面。

```
【追加するもの】
[x4] ラグビー部の今年の出店区画はB1に決まった        ←《記録》 at:09-12
[x5] B1は人通りの多い場所である                      ←《記録》 at:09-12
[x6] ラグビー部が立地に依存しない案を選ぶ必要はない  ← {x4, x5} at:09-12

【張るエッジ】
x4 ⊣ x2   （「まだ分からない」がもう成り立たない）
x6 ⊣ x3   （判断そのものを否定する）

【書き換えるもの】
なし
```

これで自動的にこうなる。

| 時点 | 生きている判断 | 倒れたもの |
|---|---|---|
| 09-05 | x1 x2 x3 x7 x8 | なし |
| 09-12 | x1 x4 x5 x6 | x2 x3 x7 x8 |

### 5.3 rebut の意味を正確に

> `rebut` ＝「その主張は**偽である**」ではなく「その主張は**もう成り立たない**」

反証と失効を区別しない。x2（まだ分からない）は当時は正しかった。間違っていたのではなく、期限が切れただけ。**どちらだったかは `at` を見れば分かる。**

### 5.4 時点復元

`at <= T` のノードとエッジだけに絞って計算し直す。

09-05 でフィルタすると、x4〜x6 と2本の rebut が消えるので x2 が生き返り、当時の判断状態がそのまま出る。

### 5.5 否定で終わっても、それでよい

x6 は「必要はない」としか言っていない。**では何をするのかは、まだ誰も決めていない。**

このとき、代案を記録者が書いてはならない（→ D1）。空いた穴は自動で検出される。

```
空白（決め直しが要る）: x3 x7 x8
```

「立地に依存しない案を選ぶ」も「仕掛けを組み込む」も「キック的当てを併設する」も、根拠を失ったまま代わりがない、と出る。これが次に議論すべきことである。

## 第6部 自動で出てくるもの

すべて到達可能性と空欄判定だけで計算される。**意味理解は使わない。**

### 6.1 基本計算

| 名称 | 定義 |
|---|---|
| 与件か主張か | 入力エッジがゼロなら与件 |
| 上流（根拠） | `from` をたどった推移閉包 |
| 下流（要再検討） | `to` をたどった推移閉包 |
| **倒れる範囲** | 下の定義を参照 |
| **空白** | 倒れた主張が支えていたもののうち、他に生きた支えがないもの |
| 時点復元 | `at <= T` で絞って再計算 |

#### 倒れる判定の正確な定義

```
ノード x が倒れる
  ⟺ x への support エッジが1本以上あり、
     そのすべてについて、from の中に倒れたノードが含まれる
```

support エッジが1本もないノードは、この規則では倒れない。

### 6.2 NextAction

| 項目 | 定義 | 意味 |
|---|---|---|
| **情報をそろえる** | `情報不足` から到達できる主張 | それぞれが何件の判断を止めているかを併記する |
| **決め直す** | 「空白」 | 根拠を失ったまま代わりが立っていない判断 |
| **根拠が直感だけ** | 支えが `直感` のみで、rebut を受けていない主張 | 意識的に直感として採るか、支えを足すか |
| **使われていない資料** | 出力ゼロ・rebut なし・支えが出所（`直感` 除く）のみ | 見落としの可能性 |

### 6.3 論証の穴

| 項目 | 定義 |
|---|---|
| 支えなし | 入力エッジがゼロの主張（出所すら引いていない） |
| 未検証の前提に支えられた結論 | `経験則` `伝聞` `直感` から到達できる主張 |
| 隠れた価値判断 | `方針` から到達できる主張 |

> 実例：出店会議では `経験則` から到達できる主張が全体の72%だった。一次資料は12件のみ。また、`伝聞` 1件（先輩の口頭の証言）が、去年の赤字を経由して今年の仕入れ方針すべての根になっていた。

### 6.4 診断の出し方

**断定形で出さない。**

```
✗  この2つは矛盾しています
○  この2つは両立しますか。条件が違う可能性があります
```

誤検出のコストが大きく下がる。的外れな指摘が3回続けば、使う人は通知を切る。

## 第8部 よくある間違い

### 8.1 言われていないことを書く ★最も多い

一般論として正しくても、**発言から復元できないなら書かない。**

```
発言：「立地に依存しない案を選ぶ必要はなくなった」

✗  ラグビー部は、B1の人通りを活かした案を選ぶべきである
     → 誰も言っていない。場所ガチャ対策そのものをやめて
       別の勝ち筋を探す可能性もある

○  ラグビー部が立地に依存しない案を選ぶ必要はない
```

「否定で終わらせず代案を立てるべきだ」は**議論を診断した結果であって、記録するときの規則ではない。** 両者を混同しない。

### 8.2 出所を上げる

```
✗  「先輩が1,200食売れたと言っていた」 →《記録》
○                                    →《伝聞》
```

これを `記録` にすると、失敗の根本原因がグラフから見えなくなる。

### 8.3 橋を埋めたまま反論しようとする

刺す先がないことに気づいたら、それは Step 1 で割り足りていない合図。**エッジの種類を増やして解決しようとしない。** ノードを割れば書ける。

### 8.4 「でも」を全部 rebut にする

「でも」「ただ」の大半は、認めたうえでの追加であって反論ではない。全部つなぐと対立だらけの読めないグラフになる。

### 8.5 迷ったら連言にする

逆である。連言は波及を過大に出す。迷ったら独立にする。

### 8.6 疑問を全部「条件形」にする

第3部 Step 6 の判定を必ず通す。片方は「分からない形」で書かないと、意味が逆になる。

### 8.7 フィールドを足して解決しようとする

「これは書けない」と思ったとき、ほぼすべてはノードを割れば書ける。フィールドや `kind` を増やす前に、割れないかを疑う。

> 実例：以前この形式には `warrant`（根拠）フィールドと `undercut`（根拠を崩す）というエッジ種があった。どちらも「橋をノードとして割る」ことで不要になった。

## 第9部 限界

現時点で分かっている、この形式で書けないこと。

| 限界 | 状況 | 現在の対処 |
|---|---|---|
| **エッジに反論できない** | 「その事実は認めるが、そこからその結論は出ない」 | Step 1 で橋を割れば、ノードへの反論として書ける。**割っていないときにだけ発生する** |
| **排他が書けない** | 「Aだ」と「Aでない」が両立しないことを機械が読めない | 相互に rebut を張る。ただし機械は排他とは解釈しない |
| **言い換えの同定ができない** | 同じ主張が別IDで重複する | 人間の規律のみ。埋め込み検索が必要 |
| **診断のチューニング未完** | 規模が増えると一部の検出が誤爆する | 実データで確認済みの既知課題 |

### 診断の誤検出について

**誤検出を出さないことが、多く検出することより重要。** 的外れな指摘が続けば通知が切られ、仕組み全体が使われなくなる。

網羅性より適合率を優先する。これは「多く見つけたい」という自然な直感と逆向きなので、意識的に守る必要がある。

## 付録B 最小実装

### データ構造

```js
const N = [
  {id:"情報不足", src:true, text:"情報不足"},
  {id:"x2", at:"2026-09-05", say:"18",
   text:"ラグビー部の今年の出店区画が良い場所か悪い場所か、まだ分からない"},
];

const E = [
  {id:"e1", at:"2026-09-05", kind:"support", from:["情報不足"], to:"x2"},
  {id:"e9", at:"2026-09-12", kind:"rebut",   from:["x4"], to:"x2",
   note:"抽選の結果が出たため、この時点で成り立たなくなった"},
];
```

### 倒れる範囲の計算

```js
function collapse(nodes, edges, seeds){
  const SUP = {};
  nodes.forEach(x => SUP[x.id] = []);
  edges.filter(e => e.kind === "support").forEach(e => SUP[e.to].push(e.from));

  const dead = new Set(seeds);
  let changed = true;
  while (changed) {
    changed = false;
    for (const x of nodes) {
      if (x.src || dead.has(x.id)) continue;
      const groups = SUP[x.id];
      if (!groups.length) continue;
      if (groups.every(g => g.some(p => dead.has(p)))) {
        dead.add(x.id);
        changed = true;
      }
    }
  }
  return dead;
}
```

### 時点復元

```js
function view(N, E, T){
  const nodes = N.filter(x => x.src || x.at <= T);
  const edges = E.filter(e => e.at <= T);
  const seeds = edges.filter(e => e.kind === "rebut").map(e => e.to);
  return collapse(nodes, edges, seeds);
}
```

### 空白の検出

```js
function holes(nodes, edges, dead){
  const OUT = {};
  nodes.forEach(x => OUT[x.id] = []);
  edges.filter(e => e.kind === "support")
       .forEach(e => e.from.forEach(f => OUT[f] && OUT[f].push(e.to)));

  const h = new Set();
  dead.forEach(d => OUT[d].forEach(t => { if (dead.has(t)) h.add(t); }));
  return [...h];
}
```

## まとめ

| 項目 | 内容 |
|---|---|
| ノードのフィールド | `id` `text` `at` （`say` 任意） |
| エッジのフィールド | `id` `kind` `from[]` `to` `at` （`note` 任意） |
| エッジの種類 | `support` `rebut` の2つ |
| 出所語彙 | `記録` `伝聞` `経験則` `直感` `方針` `情報不足` の6語 |
| 運用 | 追記のみ。訂正は rebut |
| 最重要の規則 | `from` にはIDしか書かない |
| 次に重要な規則 | 「〜のため」があったら割る／言われていないことを書かない |
